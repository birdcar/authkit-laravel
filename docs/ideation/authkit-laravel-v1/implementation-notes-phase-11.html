PipesManager — connect()/disconnect()/import() trimmed per the spec's own scope-traceability directive

Context
Spec §2 flags these three methods (plus PipesInvalidImportException, Failure Mode 3, and Open Item 3) as "a genuine scope expansion beyond the contract, not a restatement of it": both canonical scope statements — contract-data.json scope.mvp[14] ("$user->connectedAccounts(), access-token fetch with auto-refresh, org provider-config passthrough") and execution.phases[10].notes — name exactly three capabilities. The spec directs that an approver consciously ratify the expansion "or, absent that ratification, trim Component 1 back to the four contract-traceable methods."
Decision
Trimmed. This is a headless run with no approver present, so the spec's no-ratification branch governs: shipped connectedAccounts(), accessToken(), providerConfig(), configureProvider(); deferred connect()/disconnect()/import() and the 422 import exception to a future contract amendment. Direct precedent: Phase 8 cut expireApiKey() under the same class of directive. Missing-scope surfacing (Failure Mode 2) is not part of the flagged expansion, so the reauthorization URL is still fetched eagerly on the exceptional branch — via a private authorizeDataIntegration call instead of a public connect().
Alternative
Shipping all seven methods as the spec's Component 1 snippet shows — rejected because the spec itself frames that as requiring conscious ratification no headless run can grant, and the expansion "reading as already-approved" is exactly what §2 warns against.

Registration — no AuthkitServiceProvider change; PipesManager is auto-wired, not a singleton

Context
Spec §6 says to bind PipesManager as a container singleton in register(). The landed harness contradicts this twice over: every client-holding service is deliberately not a singleton (a singleton pins the pre-fakeWorkosResponses() client manager — the provider's own comments at the AuditLogManager/VaultCrypto bindings), and Phase 12's four managers (Invitation/JwtTemplate/CorsOrigin/Group) ship with no provider binding at all — plain constructor auto-wiring of the Contracts\WorkosClientManager contract.
Decision
Follow the landed pattern: PipesManager constructor-injects the contract and resolves by auto-wiring (non-singleton); Authkit::pipes() + the facade @method line are the only registration surface. The MockHandler suite exercises this implicitly — a pinned singleton would make every test in the suite fail on a stale handler stack.
Alternative
Spec-literal singleton() — rejected as a known test-harness footgun (Phase 9's recorded rationale); a redundant bind() — rejected because Phase 12 established that auto-wiring needs no explicit binding for concrete managers.

PipesTest — MockHandler injection via UsesWorkosMockHandler::fakeWorkosResponses() (spec Open Item 2)

Context
The spec's beforeEach assumed a WorkosClientManager::fake(MockHandler) method, flagged as unconfirmed (Open Item 2). No such method exists; the landed mechanism is the tests/Concerns/UsesWorkosMockHandler trait, whose fakeWorkosResponses(array) binds a fresh HandlerStack instance (with history middleware) and forgets the client-manager singleton.
Decision
Replaced the spec's setup hook wholesale with uses(UsesWorkosMockHandler::class) + per-test fakeWorkosResponses(), matching every landed MockHandler suite (GroupsTest precedent). Wire assertions ride workosRequestHistory. Spec Open Item 1 resolved the assumed way: Contracts\WorkosClientManager::client(): \WorkOS\WorkOS, constructor-injected.
Alternative
Adding a fake() method to the client manager to match the spec snippet — rejected: it would duplicate existing, proven test infrastructure to satisfy an assumption the spec itself marked for confirmation.

HasWorkosUser — workos_id guard authored locally (no Phase 2 requireWorkosId() exists)

Context
The spec's trait snippet reads $this->workos_id raw and says to prefer a Phase 2 guard method "if Phase 2 lands" one. Phase 2 landed no such guard, and a raw property read is mixed at PHPStan level 7 — every landed trait reads getAttribute('workos_id') with is_string narrowing and throws a descriptive RuntimeException for never-synced models (InteractsWithWorkosApiKeys::workosApiKeyOwnerId() precedent).
Decision
Added a private workosPipesUserId(): string to the trait mirroring that precedent; both conveniences call it, so an unlinked user fails loudly before any HTTP request (covered by a test asserting zero requests reach the mock handler).
Alternative
Raw $this->workos_id access (spec-literal) — fails static analysis and would send userId: '' to WorkOS for never-linked users, turning a local state error into a confusing remote 4xx.

Workbench demo — controller written by hand; routes reshaped around the trimmed surface

Context
Spec Component 6 scaffolds PipesController with php artisan make:controller and registers pipes.index/pipes.connect/pipes.disconnect. No artisan generators run inside workbench/ in this harness (Phase 10 precedent — Testbench drives the skeleton), and the connect/disconnect actions wrap methods this phase trimmed. workbench/app is PHPStan-analysed at level 7, so $request->user() needs narrowing before trait-method calls.
Decision
Wrote workbench/app/Http/Controllers/PipesController.php directly (first controller in the workbench — new directory) exercising the full shipped surface with zero WorkOS\ references: pipes.index (trait connectedAccounts()), pipes.token (trait pipe(), 404 on not-connected, redirect to the exception's reauthorizationUrl on drift — the raw token value deliberately not echoed), and pipes.providers/pipes.providers.update (org passthrough, organization from query/body per the depth-extensions convention). abort_unless($user instanceof User, 401) provides the level-7 narrowing.
Alternative
Keeping the spec's three routes with connect/disconnect stubs — rejected: the demo would advertise surface the package no longer ships, defeating its role as the Phase 13 grep-enforcement exemplar.
