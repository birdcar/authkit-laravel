Implementation Notes — Phase 13

Integration, Quickstart & Release Readiness — decisions not covered by the spec, for human review.

AuthkitConfig — found bug: baseUrl() ignored the emulate override (the phase's one src/ change)

Context
The spec allows src/ changes only for a real gap found by this phase's audits. The Acceptance suite's first full emulate login found one: AuthkitConfig::baseUrl() read authkit.base_url directly, so the workos guard's JWKS verification (and logout URLs) talked to production WorkOS even with authkit.emulate.enabled on — an emulate-backed login minted sessions the guard then rejected. No landed test had ever authenticated the guard against emulate (all guard tests are MockHandler-backed), so the gap was invisible until now.
Decision
Made AuthkitConfig::baseUrl() emulate-aware, mirroring WorkosClientManager::fromConfig()'s exact branch. Cites Phase 1's emulate promise: the whole package follows the override, not just the SDK client. Two call sites benefit (guard registration, logout request).
Alternative
Passing the client manager's base URL into the guard instead — rejected as a wider refactor; the config accessor is the single shared source both call sites already use.

Service provider — found gap: no default workos guard entry (second pre-authorized src/ fix)

Context
progress.md's "Known Gaps To Fold In Later" recorded: authkit:install does not write config/auth.php guard/provider entries, so "a consumer running only the installer gets 'Auth guard [workos] is not defined'" — explicitly assigned to be fixed "before/within Phase 13 acceptance". The spec's Assumed Interfaces table names the Phase 1 promise as "registers routes + guard"; routes and the guard DRIVER were wired, the guard ENTRY never was — exactly the spec's found-bug clause ("a mechanism named in the contract that never got wired into AuthkitServiceProvider").
Decision
register() now seeds auth.guards.workos => ['driver' => 'workos', 'provider' => 'users'] with the consumer's own entry winning the merge — byte-for-byte the landed authkit-key default-entry pattern sitting directly above it. Two IdiomCoverage tests prove the seed and the consumer-wins merge. Quickstart step 3 and the Boost skill drop the config/auth.php edit (the model trait/contract wiring remains — the callback requires WorkosUser).
Alternative
Teaching authkit:install to edit config/auth.php — rejected: config file mutation is fragile across app styles, and the provider-seeded default (consumer wins) is the pattern this repo already established for authkit-key.

Component 1 — dedicated acceptance emulate seed instead of expanding the shared fixture

Context
The spec expands the root emulate seed with roles/permissions/memberships. Landed reality: seeds live per-suite under tests/Fixtures/, and AuthorizationTest's emulate smoke asserts EMPTY environment role/permission lists against the shared fixture (emulate 0.6.0's non-empty payloads are unparseable by SDK v9.1 — Phase 5's recorded finding). Seeding roles there would break a landed suite.
Decision
New tests/Fixtures/workos-emulate-acceptance.config.yaml (pinned user/org ids, membership with admin role carrying posts.manage, invitation, connect application, jwtTemplate) — the established dedicated-seed pattern (api-keys, depth fixtures). The workbench seeder's primary user matches its identity so composer serve against this seed links the same row. Also: emulate 0.6.0's seed schema DOES support memberships (organizations[].memberships by email) — Phase 3's "cannot seed memberships" note is outdated.
Alternative
Expanding the shared fixture as written — rejected: breaks AuthorizationTest's empty-list wire smoke.

Component 5 — Vault cast demo reuses VaultDemoRecord; Post secret_note changes dropped

Context
The spec adds a Vaulted-cast secret_note column to Post (+ migration + factory value) "to reuse the existing demo model instead of introducing a new one". Phase 9 already shipped exactly such a model: VaultDemoRecord with a Vaulted secret column.
Decision
VaultDemoController round-trips through VaultDemoRecord; the Post migration/factory/model changes are dropped (three fewer files, same proof, honoring the spec's own reuse rationale). Vault facade calls reconciled to the landed API: Vault::set($keyContext, $name, $value) / Vault::get($name)->value, and the filesystem driver's config shape is ['driver' => 'vault', 'disk' => 'local'] (not 'wraps'). Emulate has zero Vault routes, so the route documents that it needs live credentials — Vault's CI proof stays in its MockHandler suite.
Alternative
Adding secret_note to Post anyway — rejected as duplicate demo surface.

Component 6 — Acceptance mechanics reconciled to landed code

Context
Spec placeholders: Authkit::users()->getUserByExternalId() (no such accessor exists), $this->actingAs($user, 'workos') before $user->can() (the claims Gate hook reads the guard's sealed-session claims — actingAs carries none, so it would prove nothing), and a route middleware alias 'workos' (none exists).
Decision
External-id linkage asserted through the container-bound WorkOS\Service\UserManagement (the landed test-side accessor pattern); can() assertions made through real HTTP requests with the sealed cookie against the workbench /dashboard and /demo/rbac routes (positive AND negative permission), matching AuthorizationMockTest's precedent and proving the demo surface at the same time; routes use auth:workos. The suite boots the actual workbench app via Testbench's WithWorkbench. Issuer config cleared in-test (enforcement is opt-in pending the token audit; emulate mints its own base URL as iss). JSON requests carry test cookies only with withCredentials() — a Laravel test-harness quirk worth knowing.
Alternative
Faking claims via actingAs or MockHandler — rejected: the contract requires the emulate-backed wire journey.

Component 8 — IdiomCoverage: both Open-Item gaps closed, without fabricating a Blade directive

Context
The spec left two named gaps: the route-macro assertion (no confirmed name at authoring time) and the Gate/Blade-directive assertion, with instructions to close both once real names were known and never to ship a tautology.
Decision
Route macro confirmed and asserted: Route::hasMacro('workosWebhooks'), plus Request::hasMacro('organization'). For Gate/Blade: no phase shipped (or promised, in any spec) a custom Blade directive — the landed mechanism behind the contract's "Gate/Blade directives" idiom is the pair of Gate::before hooks, which Laravel's built-in @can rides. Asserted behaviorally: an undefined ability allowed solely via a WorkosApiKeyActor's key permissions proves the hook is registered; the claims-side hook is proven end-to-end by the Acceptance suite.
Alternative
Inventing and registering a new Blade directive to satisfy the idiom's letter — rejected: that would be new public API this release phase must not add.

Component 9 — zero-SDK grep test skipped on Windows

Context
The test shells out to real grep (the spec's drift-free choice); Windows CI cells run vendor/bin/pest but have no grep.
Decision
Skip on PHP_OS_FAMILY === 'Windows' with an explanatory reason; the ubuntu matrix cells carry the gate. Also: the path resolves from the test file (dirname(__DIR__, 2)) because base_path() in package tests is the Testbench skeleton, not this repo — the spec snippet's base_path('workbench') would grep an empty directory and pass vacuously.
Alternative
A PHP reimplementation of the regex (runs everywhere) — rejected per the spec's own drift argument.

CI workflow — priming step instead of an external emulate boot

Context
The spec's CI component assumed an externally-booted emulate at a fixed port with WORKOS_BASE_URL/WORKOS_API_KEY exported. Landed reality (spec Open Item 6's anticipated branch): every emulate-backed suite boots its own EmulateServer per suite with its own port and seed; nothing reads those env vars, and TestCase pins all config hermetically.
Decision
The ubuntu-only CI step warms the npx cache and runs --validate-config across all four seed fixtures — de-flaking in-suite cold boots (60s health budget) and failing loudly on a malformed seed. Windows exclusion is by EmulateServer design, not a CI gap. The spec's Windows Start-Process failure mode is moot under this architecture.
Alternative
A bespoke background boot + health poll + env export — rejected as dead configuration nothing consumes.

Component 10 — quickstart has 5 numbered steps, not the spec's 4

Context
The spec's draft omitted auth wiring because it assumed authkit:install "registers routes + guard". The landed installer publishes config/migrations and writes env keys but deliberately does not edit config/auth.php or the User model — so a 4-step doc would leave the human trial without a working guard, failing the very criterion the doc exists to meet.
Decision
An honest step 3 ("wire your user model and guard") was added: 5 numbered top-level steps, within the contract's mechanical ≤5 ceiling (grep check prints 5). Phase 4's events/webhooks/dev-wiring content is retained below the steps as unnumbered reference sections.
Alternative
Folding the wiring into step 2's sub-details to keep the 4-step margin — rejected: two file edits hidden in prose is how a timed trial stalls.

Component 4 — listener hand-written; trigger command uses the org trait

Context
The spec generates LogWorkosEvents via make:workos-listener from the workbench context and leaves demo:trigger-event's write unspecified ("whichever package-level call actually exposes a mutating write").
Decision
LogWorkosEvents is hand-written under workbench/app/Listeners (the recorded Phase 10/11 convention: no artisan generators inside workbench; the generator itself is covered by MakeWorkosListenerTest), registered via Event::listen in WorkbenchServiceProvider::boot(). demo:trigger-event creates a local Organization — HasWorkosOrganization's observer registers it with WorkOS, producing organization.created with zero SDK references.
Alternative
Running the generator against the Testbench skeleton and relocating the file — rejected: produces churn in a shared skeleton other parallel suites read.
