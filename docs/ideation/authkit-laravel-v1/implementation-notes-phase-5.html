Implementation Notes — Phase 5

authkit-laravel-v1 · Authorization (RBAC + FGA) · 2026-08-09

Test paths — emulate downgraded to MockHandler for RoleManager CRUD, assignment, and FgaChecker

Context
Spec §8 puts RoleManager CRUD/assignment and FgaChecker::check() on the emulate path, with two named Open Items requiring empirical verification (check's resource_type handling; membership seedability), each with a sanctioned MockHandler fallback.
Decision
Verified empirically against a live @workos/emulate@0.6.0: memberships ARE creatable at runtime (POST user_management/organization_memberships), but the authorization surface has drifted from SDK v9.1 — the check endpoint 422s on the SDK's permission_slug (expects permission), assignRole 422s on role_slug (expects role_id), and role/permission/resource response payloads use a legacy shape missing keys the SDK's fromArray parsers require (resource_type_slug, permissions, system, name). Every non-empty-response case therefore moved to MockHandler per the spec's own fallbacks; one emulate smoke test remains (empty env-role + permission list round-trips, which the SDK parses), matching the one-smoke-test-per-suite precedent from Phases 2–3.
Alternative
Keeping role/permission CRUD on emulate as §8's table intended — impossible until emulate catches up to the current Authorization API shapes; the drift details are recorded in the suite's top-of-file comment and context-map.md so a future emulate bump can restore the path.

WorkosResourcePolicy — instanceof WorkosResource contract instead of class_uses_recursive

Context
Spec §4.6 gates the policy's generic check on in_array(HasWorkosResource::class, class_uses_recursive($resource), true) and then calls trait methods on the model. PHPStan level 7 (enforced by composer analyse) cannot type a "uses trait" narrowing — a Model&HasWorkosResource annotation is an unresolvable type.
Decision
Added a Contracts\WorkosResource interface (the four workosResource* methods), satisfied by the trait and declared via @phpstan-require-implements; the policy checks instanceof WorkosResource. This mirrors the package's established WorkosUser/HasWorkosUser pairing (trait satisfies contract, consumers instanceof the contract), so it is the pattern-conformant translation of the spec's intent. Consuming models add implements WorkosResource alongside use HasWorkosResource; the LogicException message names both.
Alternative
method_exists() duck-typing with is_string narrowing on every return — PHPStan-clean but unlike anything else in the codebase, and it hides the contract instead of naming it.

§3a seam — Phase 3 landed first, so the resolver default stays real

Context
Spec §3a/§7 assume Phase 5 may land before Phase 3 and therefore author ResolvesOrganizationMembershipId, the provider bindIf, and a NullMembershipResolver config default. Phase 3 (commit 952e344) had already shipped the contract, the bindIf, the config key, and a real MembershipProjectionResolver default, plus the guard's accessTokenClaims() accessor.
Decision
Did not re-author any of it and kept MembershipProjectionResolver as the shipped default — the seam §3a exists to fill is already filled with the projection-backed resolver the spec says is "Phase 3's job". Phase 5 added only what was still missing: the HasAccessTokenClaims interface (guard now implements it), NullMembershipResolver as an explicit fail-loud opt-out (used by the MembershipNotResolvedException test exactly as §8 prescribes), and MembershipNotResolvedException itself.
Alternative
Flipping the config default to NullMembershipResolver to match §6's table literally — strictly worse for consumers (implicit FGA checks would throw until reconfigured) and contrary to the spec's own orchestration note that the real binding is the desired end state.

ClaimsGateHook — singular role claim checked alongside, not instead of, roles[]

Context
Spec §4.1's snippet uses the singular role claim only when the plural roles key is absent ($claims['roles'] ?? ...), while its prose says the hook "checks both defensively" pending the Phase 1 token audit.
Decision
Implemented the prose: permissions[], roles[], and singular role are each checked, and garbage-shaped claims (non-array lists, non-string entries) are filtered rather than fatal — the hook must never error or return false on any token shape. Covered by a dataset test asserting non-false across garbage shapes.
Alternative
The snippet's ??-fallback — it would silently skip a valid singular claim whenever a plural key exists but is empty or malformed, and would pass a non-array plural claim straight into in_array().

ResourceManager::deleteByExternalId — false cascades to an omitted parameter, not cascade_delete=0

Context
Spec §4.5 gives the wrapper bool $cascadeDelete = false; the SDK's parameter is ?bool = null and omits the query parameter entirely when null.
Decision
Kept the spec's bool signature but translated false to null at the SDK boundary, so the default delete matches the API's own default wire shape instead of sending cascade_delete=0 on every call.
Alternative
Passing the bool straight through — puts a redundant cascade_delete=0 on every default deletion and couples the package's wire shape to http_build_query's bool rendering.

Workbench fixtures — SoftDeletes documented via a subclass, not on Project itself

Context
Spec §8 suggests giving the workbench fixture SoftDeletes "for this one test" to document Failure Mode 8 (soft delete still deletes the remote FGA resource).
Decision
Added a SoftDeletableProject subclass sharing the projects table (which carries deleted_at) instead of putting SoftDeletes on Project — the main fixture keeps hard-delete semantics for the trait's ordinary created/deleted tests, and the divergence test uses the subclass explicitly.
Alternative
SoftDeletes directly on Project — every trait test would then exercise soft-delete semantics, leaving the ordinary hard-delete path untested.
