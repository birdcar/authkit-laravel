Implementation Notes — Phase 9

authkit-laravel-v1 · Vault · 2026-08-09

VaultCrypto / VaultManager — constructor-inject the WorkosClientManager contract, not \WorkOS\WorkOS (spec Open Item 1 resolved)

Context
Spec §4's class bodies constructor-inject \WorkOS\WorkOS $client and Open Item 1 flags this as an assumption: "If Phase 1 instead exposes it only through an intermediary method ... every constructor-injected \WorkOS\WorkOS $client needs updating."
Decision
Phase 1 binds only Contracts\WorkosClientManager (singleton with a client(): WorkOS accessor); no \WorkOS\WorkOS container binding exists. Both classes inject the contract and call ->client()->vault() per call — the Phase 5/7 precedent — so the memoized client (and any swapped Guzzle handler stack) is picked up lazily.
Alternative
Adding a \WorkOS\WorkOS container binding for the spec's literal signature — a second SDK-access seam the Phase 1 design deliberately avoids, and one the MockHandler harness (which forgets the manager instance) would not refresh.

Service provider — VaultCrypto/VaultManager registered as bind(), not the spec's singleton()

Context
Spec §6 registers both as $this->app->singleton(...).
Decision
Registered with bind() (transient), mirroring the provider's own comment on UserManagement/SessionManager/PKCEHelper: "Bound (not singleton) so swapping the handler stack mid-test is picked up." UsesWorkosMockHandler::fakeWorkosResponses() works by forgetting the client-manager instance; a singleton VaultCrypto resolved before the fake would pin the pre-swap manager and every crypto call would hit the stale handler. Both classes are stateless, so nothing is lost.
Alternative
Spec-literal singletons — correct in production but silently incompatible with the landed test harness's swap mechanism, failing exactly the way the harness comment warns about.

Storage::extend('vault') — the creator closure must not touch $this (RebindsCallbacksToSelf)

Context
The spec's boot() snippet is a plain closure, and a first implementation pass factored the key-context narrowing into a private provider method called via $this->vaultDiskContext(...) inside the closure.
Decision
Laravel 12's FilesystemManager::extend() rebinds the callback's $this and its class scope to the FilesystemManager (RebindsCallbacksToSelf) — the identical trap registerGuard() already documents for Auth::extend(). PHPStan caught the miswire ("Call to an undefined method ...::vaultDiskContext()"); the narrowing is inlined into the closure and a comment mirrors the registerGuard warning.
Alternative
A static helper called via self:: — also rebound (class scope moves too), same fatal at first disk resolution.

config/authkit.php — Phase 1's dead vault.key_context placeholder replaced by the phase's real schema

Context
Spec §5 says the phase "only adds its own subtree" (key_context_resolver, filesystem.max_encrypt_bytes). The file already carried a vault subtree holding a single 'key_context' => env('AUTHKIT_VAULT_KEY_CONTEXT') entry that no code in any landed phase reads, and which no component of this phase's design (context comes from the resolver, not a static env string) can consume.
Decision
Replaced the placeholder with the two real keys. Leaving it would be an active silent-failure surface: a user setting AUTHKIT_VAULT_KEY_CONTEXT expecting it to steer encryption would get no effect at all — the exact class of silent key-context failure §8 warns about. max_encrypt_bytes gained an AUTHKIT_VAULT_MAX_ENCRYPT_BYTES env knob per the file's every-scalar-is-env-backed convention.
Alternative
Keeping both keys side by side — no consumer, misleading name adjacency (key_context vs key_context_resolver), and the config schema test would happily bless the dead entry forever.

ResolvesVaultKeyContext binding — guards beyond the spec's BindingResolutionException catch

Context
Spec §6's binding only catches BindingResolutionException. A config value naming a resolvable class that does not implement the interface (e.g. stdClass), or a non-string value, would escape as a TypeError deep inside VaultCrypto's constructor with no mention of the config key.
Decision
Mirrored the landed membership_resolver binding precedent: is_string narrowing plus an instanceof check, both throwing the same InvalidVaultKeyContextResolverException; the factory's $previous parameter is optional to serve the instanceof path. All failure shapes now name authkit.vault.key_context_resolver.
Alternative
Spec-literal try/catch only — leaves two misconfiguration shapes failing with raw container/type errors, contradicting the failure-mode row the binding exists to fix.

DefaultVaultKeyContextResolver — override merge narrows to array<string, string>, stringifying scalars

Context
Spec §4.1 merges a model's vaultKeyContext() override with a bare array_merge(); the SDK's createDataKey(array $context) is typed array<string, string> and PHPStan level 7 rejects merging an unvalidated array into that shape.
Decision
The merge keeps string keys only and casts scalar values (int tenant ids, bools) to string rather than dropping them — dropping a context key would be a silent key-context drift, the phase's own headline failure mode. Non-scalar values are ignored. Same-key semantics match array_merge (override wins, base keys survive unless redefined); the override hook still short-circuits ahead of the org duck-type hook exactly as specced.
Alternative
Strict is_string-only filtering (drops an int tenant id → two tenants silently share a KEK) or throwing on non-strings (turns a recoverable representation issue into a runtime crash mid-save).

Tests — UsesWorkosMockHandler instead of the spec's raw fakeVaultRoundTrip(); interface-vs-class toThrow nuance

Context
Spec Open Item 2 says to prefer a Phase 1 shared MockHandler helper over the spec's self-sufficient fakeVaultRoundTrip() (which constructs new WorkOS(...) directly) if one exists.
Decision
The landed UsesWorkosMockHandler::fakeWorkosResponses() is that helper; every Vault test routes through it (queue assertions via $this->workosMockHandler->count(), wire assertions via $this->workosRequestHistory). The same-key round-trip pattern is kept per file as a small response builder. One nuance: WorkOSException is an interface, and Pest's toThrow() treats non-class_exists strings as message substrings — the outage test catches the concrete ServerException and asserts instanceof WorkOSException instead.
Alternative
Spec-literal app()->instance(WorkOS::class, ...) — bypasses the client-manager seam the whole package resolves through, so the code under test would exercise a client the production path never constructs.

VaultFilesystemAdapter::readStream() — native mixed return for the 100% type-coverage gate

Context
PHP has no resource return type; the contract method is untyped and pest's type-coverage plugin does not count the @return resource|null docblock (suite gate is --min=100).
Decision
Declared : mixed natively (legal covariance against the untyped interface method) and kept the docblock as the real contract.
Alternative
Lowering the type-coverage floor or excluding the file — both weaken a repo-wide gate for one unrepresentable type.

Pre-existing parallel flake observed once: InstallIdempotentTest's config republish raced a sibling worker's app boot

Context
One composer test run failed in AuthenticationFlowTest with array_merge(): Argument #2 must be of type array, int given inside mergeConfigFrom() — require of a mid-rewrite skeleton config/authkit.php returns int 1, so config('authkit') was momentarily an int. InstallIdempotentTest documents this exact "config-file race" (it republishes with --force into the skeleton config dir shared across parallel workers); this phase's config edit changed the file hash, making the rewrite non-trivial for the first time since Phase 2.
Decision
Not fixed here — out of this phase's scope (no Vault file is involved; the race predates the phase and is owned by the install-test design). Recorded so Phase 13's CI recipe work (which already owns the config:cache smoke-check follow-up) can pick it up. Validation was re-run and is green.
Alternative
Reworking InstallIdempotentTest's publish lifecycle in this commit — touches an unrelated Phase 1 test file, against the one-feature-at-a-time working rule.
