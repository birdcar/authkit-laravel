Implementation Notes — Phase 3

AuthKit Laravel v1 · Organizations & Org Context · 2026-08-09

Baseline — pinned app.key in tests/TestCase.php (repair before scope)

Context
Session-start baseline was RED: 10 AuthenticationFlowTest errors, "No application encryption key has been specified." The Testbench skeleton's .env (which carried APP_KEY) is purged on every composer install, so any suite passing through the web group's EncryptCookies failed on a fresh checkout. Phase 2's green run had leaned on leftover skeleton state.
Decision
Pin app.key in TestCase::getEnvironmentSetUp() (the well-known Testbench literal), making the suite hermetic. Verified: 124/124 pass afterwards, matching Phase 2's recorded evidence exactly.
Alternative
Requiring composer build before composer test in init.sh — rejected: the repo's own Definition of Done says ./init.sh alone must restart the project.

HasWorkosOrganization — static::observe() is illegal in a boot hook

Context
Spec Component 3 registers the observer via static::observe(WorkosOrganizationObserver::class) inside bootHasWorkosOrganization(). Empirically fatal: Model::observe() constructs new static to enumerate observable events, which throws "bootIfNotBooted may not be called ... while it is being booted" for every model using the trait.
Decision
Register the observer's two hooks directly: static::created([WorkosOrganizationObserver::class, 'created']) / static::deleted(...). Identical container-resolved listener wiring to what registerObserver() produces, no instance construction, and the dedicated Observer class the spec wants is preserved.
Alternative
Requiring apps to add #[ObservedBy] on their model — rejected: turns "add a trait" into two steps and breaks the spec's one-trait ergonomic contract.

Jobs — public bool $afterCommit = true fatally collides with Queueable

Context
Spec Component 4 declares public bool $afterCommit = true; on both jobs alongside use Queueable. Illuminate\Bus\Queueable already defines untyped public $afterCommit; a typed redeclaration with a different default is a fatal trait-composition conflict ("definition differs and is considered incompatible") the moment the class loads. The fatal was swallowed by Pest's output buffering, presenting as a zero-output exit-1 run.
Decision
Assign $this->afterCommit = true; in each job's constructor — same unconditional after-commit guarantee, no property redeclaration.
Alternative
Calling ->afterCommit() at every dispatch site — rejected by the spec itself (guarantee must not depend on call sites remembering).

Jobs — $tries reads authkit.organization.retry.tries

Context
The spec's config diff declares retry.tries (env AUTHKIT_ORGANIZATION_SYNC_TRIES) but its job code hardcodes public int $tries = 5; — the config key would have been dead on arrival.
Decision
Constructor assigns $this->tries from the config key (default 5, so behavior matches the spec's literal). backoff() already read its config key in the spec; now both halves of retry.* are honored, covered by a test.
Alternative
Hardcoding 5 and shipping an unused config key — rejected; this project already declined one dead config key (external_id_column) knowingly rather than minting another.

WorkosGuard — added the thin accessTokenClaims(): ?array accessor

Context
Component 9's resolver duck-types method_exists($guard, 'accessTokenClaims'), but the landed Phase 2 guard has no such method and Phase 5 (which owns the HasAccessTokenClaims interface) has not executed. As specced, the entire org-context layer (resolver, macro, facade accessor, authkit.org middleware) would be dead code returning null until Phase 5 — and this phase's own canonical test cases ("authenticated request with an org_id claim ... returns the model") could not pass against the real guard.
Decision
Added the plain public method to WorkosGuard (no interface, so no compile-time Phase 5 dependency), returning the decoded payload user() already produced — exactly the "thin accessor over data the guard's authenticate call already produced" spec-phase-5.md §4.1 instructs whichever phase needs it first to add. The resolver still duck-types precisely as specced; Phase 5 later only adds implements HasAccessTokenClaims.
Alternative
Testing against a stub guard and shipping the feature dormant — rejected: tests would pass against a fake while the real package behavior stayed broken for every consumer until Phase 5 lands.

Component 7 step 0 — Phase 5 has not landed; interface authored here

Context
The spec's order-dependent check: src/Contracts/ResolvesOrganizationMembershipId.php did not exist (no src/Authorization/ at all), confirming this phase runs before Phase 5.
Decision
Took the "no" branch verbatim: authored the interface per spec-phase-5.md §4.4's shape, added the bindIf() registration, and set the config default straight to MembershipProjectionResolver::class. One refinement: the binding is a closure reading config at resolve time (validating the class implements the interface, failing loudly naming the config key) rather than the spec snippet's register-time config() read, which would freeze the value before providers finish booting and silently accept a wrong class.
Alternative
Literal bindIf(iface, config(...)) string-concrete — rejected: register-time config snapshot plus no interface validation.

MembershipProjectionResolverTest — Authkit::check() integration case dropped

Context
The spec's second resolver test binds into "a real Authkit::check() call (reusing Phase 5's AuthorizationTest fixtures)" — but Phase 5 has not run: no Authkit::check(), no MembershipNotResolvedException, no fixtures exist.
Decision
Covered resolve() directly plus the container binding (default and config-override paths). The FGA integration assertion belongs to Phase 5's suite when it lands against this real resolver.
Alternative
Pre-building a slice of Phase 5's checker to integration-test against — rejected: out of scope and would force Phase 5 to reconcile against speculative code.

SwitchOrganizationController — SessionCookie::issue() and relative-only return_to

Context
The spec's controller hand-rolls new Cookie(...) (omitting path/domain) and redirects to raw return_to input. Phase 2's SessionCookie docblock mandates every issuer agree on name/path/domain — a hand-rolled cookie at default path / would not replace a cookie issued at a configured session.path, and raw return_to is an open-redirect primitive on request input.
Decision
Issue via SessionCookie::issue($sealed) (the repo's single sanctioned constructor) and constrain return_to to app-relative paths (must start with /, not //), falling back to /. Both covered by tests.
Alternative
Spec-literal cookie construction and unvalidated redirect — rejected: contradicts the codebase's own documented invariant and standard redirect hygiene.

Test paths — emulate downgraded to MockHandler for membership-dependent suites

Context
Spec Open Item 4 pre-authorized this: emulate 0.6.0's seed schema (users, organizations/domains) offers no way to seed a pre-existing organization membership, and a wire-true org-switch refresh would need a sealed cookie whose refresh token emulate itself minted (requiring a full browser OAuth round trip no suite in this package drives — Phase 2 set the same precedent for its refresh tests).
Decision
LoginProjectionUpsertTest and OrganizationSwitchTest are MockHandler-backed end-to-end (full callback flow, real signed fixture tokens); HasWorkosOrganizationTest keeps a true emulate round trip (create → remote verify → delete → remote 404) since organizations are fully emulate-covered. Each affected file carries a test-path note.
Alternative
Driving emulate's hosted auth UI headlessly to mint a real session — rejected: new infrastructure the contract's truth bar doesn't require, for fixture fidelity the MockHandler cases already pin byte-for-byte.
