InteractsWithWorkosApiKeys — expireApiKey() cut (spec §1/§11 scope-expansion flag resolved: not confirmed)

Context
The spec flagged expireApiKey() / ApiKeys::createApiKeyExpire as scope expansion pending sign-off: the contract's scope row and execution.phases[7].notes both name exactly two write verbs ("issue/revoke"), and the only cited justification was an unquoted "phase direction" source. The spec's directive: confirm against the phase-direction/ideation transcript, and cut if unconfirmable.
Decision
Cut. Checked contract-data.json directly: its only two "expire" occurrences are about expired JWTs in the SessionSecurity success criterion — nothing about API keys. No ideation transcript exists in the repo to confirm the phase-direction claim. Per the spec's own instruction, the trait method, its MockHandler test case, and its file-trace rows were all dropped; the shared trait ships revokeApiKey() only.
Alternative
Shipping expireApiKey() anyway — rejected because it would be a third WorkOS write verb no canonical artifact approves, exactly what the strict/express-approval contract forbids landing silently.

ApiKeysTest — emulate 0.6.0 has no org-key CREATE endpoint; create coverage moved to MockHandler, suite gets a dedicated seed file

Context
Spec §3.6/§6 assumed emulate covers org-scoped create/list/validate ("API-key org endpoints" in the template's coverage list) and assigned createApiKey()'s emulate cases accordingly, plus a tinker playground of Organization::first()->createApiKey('ci-bot').
Decision
Probed @workos/emulate@0.6.0's route source (dist/workos/routes/api-keys.js): only POST /api_keys/validations, DELETE /api_keys/:id, and GET /organizations/:orgId/api_keys exist — POST /organizations/:orgId/api_keys is unregistered and 404s. Org-scoped createApiKey() is therefore MockHandler-tested (wire-shape assertions), while the emulate suite covers what emulate really implements: seeded-key validation through the guard, Gate integration, listing, revoke-then-revalidate, and the data-shadow case. Additionally, the seed loader (dist/workos/index.js) shows an array-form apiKeys: seed REPLACES the default auth allow-list — sk_test_default stops authenticating — so the suite uses a dedicated workos-emulate-api-keys.config.yaml that re-seeds the SDK admin key, rather than extending the shared fixture and silently 401-ing every other emulate suite.
Alternative
Keeping the spec's literal emulate case list (create against emulate can never pass — a permanently red or vacuously skipped test), or seeding apiKeys into the shared fixture (breaks all other emulate-backed suites via the allow-list replacement).

ApiKeyAuthenticator / traits — spec §0 assumptions reconciled against the landed Phase 1–3 surface

Context
The delta was written before Phases 1/3 landed and assumed Authkit::client(), config('auth.providers.users.model'), and config('authkit.organization_model'), instructing the executor to substitute whatever those phases actually shipped.
Decision
Guard and traits resolve the SDK through Contracts\WorkosClientManager (constructor-injected in the authenticator, per-call app() in the traits — resolved lazily either way so the MockHandler harness's forgetInstance is honored). User model resolves via config('auth.providers.workos.model', config('auth.providers.users.model')) — the exact chain AuthKitController::userModel() and the projection listeners use — and the org model via authkit.organization.model. MissingModelConfigurationException messages name the real keys. The user model must also be Authenticatable (it becomes the request principal), enforced alongside the Eloquent check.
Alternative
Adding an Authkit::client() facade accessor for the spec's literal call shape — a second SDK-access seam Phase 1 deliberately avoided, and one the whole landed codebase already bypasses.

ApiKeyRequestGuard — RequestGuard subclass whose setRequest() clears the memoized user (Decision 10 kept in substance, not letter)

Context
Spec Decision 10 registers the guard via Auth::viaRequest(), citing RequestGuard's free per-request memoization. But stock RequestGuard::setRequest() only swaps the request — it keeps $this->user — so in any multi-request process (Octane, embedded kernels, this package's own feature tests) request #2 inherits request #1's principal: a garbage key authenticated as the previous request's actor in the suite, and would in production too.
Decision
Registered via Auth::extend('authkit-key', ...) mirroring AuthManager::viaRequest()'s internals line-for-line (same callback shape, same refresh('request', $guard, 'setRequest')), but constructing ApiKeyRequestGuard — a final RequestGuard subclass whose setRequest() nulls the memoized user first. This is the package's established rule: WorkosGuard::setRequest() already resets every per-request conclusion for exactly this reason.
Alternative
Literal Auth::viaRequest() plus test-side Auth::forgetGuards() between requests — hides a real cross-request identity leak instead of fixing it, and leaves Octane consumers exposed.

ApiKeyGateHook — invokable class instead of the spec's provider-inline closure

Context
Spec §3.4/§5 inline the API-key Gate::before callback directly in AuthkitServiceProvider::boot().
Decision
Shipped as Authorization\ApiKeyGateHook, an invokable final class mirroring Phase 5's landed ClaimsGateHook (same registration shape, same documented true/null-never-false contract, same defensive claim narrowing to list<string>), registered immediately after it in boot(). Identical behavior to the spec's closure; unit-testable directly and consistent with the codebase's one existing Gate-hook pattern.
Alternative
The literal inline closure — same semantics, but a second Gate-integration style in one provider and no direct unit-test surface.
