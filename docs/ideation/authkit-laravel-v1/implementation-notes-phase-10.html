Implementation Notes — Phase 10

authkit-laravel-v1 · Connect & MCP Auth · 2026-08-10

JwksVerifier — authored in this phase because Phase 2 shipped no reusable verifier (spec §4.1 / Open Item 1)

Context
The spec assumed a Phase 2 Authkit\Authkit\Support\Jwt\JwksVerifier generalized by URL, and warned that if Phase 2 shipped something narrower the gap "escalates to a real blocker" to be resolved rather than silently duplicated. Reality is the third branch the spec did not enumerate: Phase 2 shipped no claims-level JWKS verifier at all — session verification delegates to the vendored SDK's private SessionManager::decodeAccessToken(), and the only Phase 2 JWKS component is Http\JwksGraceCache, a Guzzle transport middleware hard-scoped to /sso/jwks/ paths.
Decision
Author src/Support/Jwt/JwksVerifier.php in this phase to exactly the §4.1 contract (same signature, RS256 allow-list before any fetch, required kid, Laravel-cache-backed TTL fetch, debounced single force-refresh on a kid miss, exp check, no iss/aud), mirroring the SDK's own verification mechanics (openssl_verify + hand-rolled DER SPKI). There is nothing to duplicate — the component simply did not exist — and creating it at the spec's assumed namespace keeps the Phase 13 reconciliation surface zero. Transport uses the container-bound HandlerStack so the MockHandler harness serves JWKS in tests.
Alternative
Stopping the phase as blocked (strict-mode HOLD) — rejected because the spec fully specifies the component's contract, making this a well-defined build item, not an underspecified gap; or calling the SDK's private machinery via reflection — rejected as obviously fragile.

Test fixtures — reused Phase 2's JwtFixture instead of creating SelfSignedJwksFixture (spec §7 note / Open Item 2)

Context
The spec's file table lists tests/Fixtures/Jwks/SelfSignedJwksFixture.php but its own note says whichever phase lands first creates the shared fixture and "the other should reuse rather than duplicating." Phase 2 landed first with tests/Fixtures/JwtFixture.php: committed deterministic RSA keys (plus a never-advertised forged key), a jwks() document builder, and a sign() with claim overrides.
Decision
Reuse JwtFixture, extending sign() with an additive $headerOverrides parameter (default [], existing callers unaffected) so the MCP suite can forge alg: none/alg: HS256 headers and unknown kids. The spec's per-run openssl_pkey_new approach was dropped with the fixture — committed keys are the landed convention (SessionSecurity determinism rationale).
Alternative
Creating the spec-named fixture anyway — rejected as exactly the duplication the spec's own note forbids.

Config — resource_indicator env var renamed from Phase 1's AUTHKIT_MCP_RESOURCE_INDICATOR to spec-10's WORKOS_MCP_RESOURCE_INDICATOR

Context
Phase 1 landed a placeholder authkit.mcp.resource_indicator reading AUTHKIT_MCP_RESOURCE_INDICATOR (its spec's config schema). Phase 10's spec §8 names the env vars WORKOS_MCP_RESOURCE_INDICATOR/WORKOS_MCP_RESOLVE_USER/WORKOS_AUTHKIT_DOMAIN, including in the workbench .env.example rows. The two specs conflict.
Decision
Follow spec-10 (the phase that actually ships the consumer of the key): grep confirmed zero consumers of the Phase 1 placeholder, and the package is unreleased, so the rename breaks nothing. Flagged here for Phase 13's release review in case the WORKOS_-vs-AUTHKIT_ prefix policy gets revisited holistically.
Alternative
Keeping the Phase 1 name — rejected because spec-10 is this phase's authority, repeats the name in three places, and the landed name had no consumers to protect.

ConnectManager — contract injection + auto-wiring instead of the §8 singleton-with-raw-client snippet

Context
Spec §8 registers ConnectManager as a singleton constructed with WorkosClientManager->client() (a captured \WorkOS\WorkOS instance). Four landed phases (5/7/8/9) already reconciled this exact snippet shape: a singleton holding a captured client pins the pre-swap client when the MockHandler harness forgets the manager mid-test.
Decision
ConnectManager constructor-injects the Contracts\WorkosClientManager contract and calls ->client()->connect() per call (RoleManager precedent, including no explicit container binding — auto-wiring resolves the bound contract). Same reconciliation recorded in the Phase 5/8/9 context maps.
Alternative
The literal spec snippet — rejected because it makes every MockHandler test observe a stale handler stack, a bug class this repo has already eliminated twice.

AuthenticateMcpToken — user-model chain gains the landed auth.providers.workos.model middle link

Context
Spec §6.3/§8 resolve the MCP user model as authkit.mcp.user_model ?? auth.providers.users.model. The landed convention everywhere else (AuthKitController::userModel(), ResolvesProjectionModels, Phase 4/8 reconciliations) inserts auth.providers.workos.model before the bare users fallback, because that is where this package's own install wiring places the WorkOS-linked model.
Decision
Chain is authkit.mcp.user_model ?? auth.providers.workos.model ?? auth.providers.users.model, with level-7 narrowing (is_string / class_exists / is_a Model) and a graceful claims-only no-op when unresolvable — consistent with F15's "no local user is not a failure".
Alternative
The spec-literal two-link chain — rejected because a consumer who followed this package's own install docs would then get silent non-resolution on every MCP request.

JwksUnavailableException — a second exception class beyond the spec's snippet, required by the normative failure table

Context
Spec §6.3's code snippet catches only InvalidMcpTokenException and JwtVerificationException (both → 401), but failure mode F-jwks-down normatively requires 503, not 401 when the JWKS is unreachable with a cold cache — a case the snippet cannot express if the fetch failure throws the same 401-mapped exception type.
Decision
Support\Jwt\Exceptions\JwksUnavailableException (deliberately NOT a JwtVerificationException subclass) signals transport failure; the middleware maps it to a 503 JSON response. Covered by two tests (connection failure and cold-cache 5xx).
Alternative
Folding fetch failures into JwtVerificationException — rejected because it makes a WorkOS outage indistinguishable from a forged token, exactly what F-jwks-down forbids.

laravel/mcp recipe — upstream AddWwwAuthenticateHeader rewrites 401 challenges on Mcp::web routes; manual happy-path curl not executable against a fixture domain

Context
Live workbench check (testbench serve + curl): the well-known document serves the exact F2 shape, and POST /mcp/demo without a token returns 401 — but with WWW-Authenticate: Bearer realm="mcp", error="invalid_token", because laravel/mcp 0.9.2's own AddWwwAuthenticateHeader route middleware overwrites any 401's challenge header (dropping this package's resource_metadata pointer on that route only). Separately, the spec's second curl (valid fixture token → non-401) cannot run live: the middleware derives the JWKS URL as https://{authkit_domain}/oauth2/jwks, and a fixture domain has no real HTTPS JWKS host to answer.
Decision
Recorded as upstream wire behavior, not a package defect: the spec itself scopes the recipe's check to status codes and declares laravel/mcp's wire format out of this package's test contract (§6.5). The 401-without-token composition proof ran live; the token-accepted path is covered by McpAuthenticationTest's valid-token case (MockHandler-served JWKS through the identical middleware). Consuming apps that need RFC 9728 discovery via the challenge header on laravel/mcp routes should know upstream rewrites it — worth a README/docs callout in Phase 13.
Alternative
Wrapping laravel/mcp's route registration to strip its middleware — rejected as fighting the upstream package inside a recipe whose whole point is showing vanilla composition; standing up a local TLS JWKS host for one manual curl — rejected as out of proportion to what it would prove beyond the automated suite.
