authkit-laravel-v1 · Feature Flags (Pennant Driver) · 2026-08-09

WorkosPennantDriver — guardClaims() reads the landed HasAccessTokenClaims contract, not the spec's claims()/workosClaims() conventions

Context
Spec §4.1's authoritative class body probes method_exists($guard, 'claims') and falls back to a workosClaims() method on the resolved user; Open Item 2 explicitly flags both as assumptions to confirm against Phase 2's real implementation.
Decision
Phase 2/5 landed WorkosGuard::accessTokenClaims(): ?array behind the Contracts\HasAccessTokenClaims interface — the same seam ClaimsGateHook and FgaChecker consume. guardClaims() therefore checks $guard instanceof HasAccessTokenClaims and calls accessTokenClaims(), which returns the raw decoded payload (carrying feature_flags when present). The test suite's stub guard pins this exact contract.
Alternative
Keeping the spec's literal method_exists probes — both would always miss (the guard has no claims(); the user trait's claims() returns the AccessTokenClaims DTO, not the raw payload), silently disabling the zero-HTTP path in production, which is precisely the degradation Open Item 2 warns about.

config/authkit.php — feature_flags block already present; spec's Modified row a no-op

Context
Spec §5 lists config/authkit.php as Modified ("Add feature_flags => ['cache_ttl' => 30] block").
Decision
Phase 1 already shipped the block, including the AUTHKIT_FEATURE_FLAGS_CACHE_TTL env knob and int cast. No config change made; the provider reads authkit.feature_flags.cache_ttl with a 30-second default exactly as specced.
Alternative
Re-writing the block redundantly — pure churn on a file this phase doesn't otherwise own.

tests/TestCase.php — PennantServiceProvider added to getPackageProviders (file outside spec's File Changes tables)

Context
Package suites register providers explicitly via Testbench's getPackageProviders(); the spec's File Changes tables never mention tests/TestCase.php, but without Pennant's provider the pennant.default/pennant.stores config and FeatureManager singleton the suite exercises would depend on skeleton package-discovery state, which composer install purges.
Decision
Added PennantServiceProvider::class after AuthkitServiceProvider::class — deliberately the dangerous D-4 ordering (our register() first, Pennant's top-level mergeConfigFrom second), which makes the "built-in stores intact" test case a real regression guard for the boot()-vs-register() decision.
Alternative
Relying on Testbench skeleton auto-discovery of vendor packages — works when the skeleton cache is fresh but is exactly the class of hidden-state dependency Phase 3's baseline repair (skeleton .env drift) already burned this repo on once.

WorkosPennantDriver — cache-key hash is sha256, not the spec's md5

Context
Spec §4.1 namespaces cache keys with substr(md5(config('authkit.client_id')), 0, 8) (Decision D-8). The repo's arch security preset (arch()->preset()->security(), predating this phase) fails the build on any md5 use.
Decision
substr(hash('sha256', ...), 0, 8) — same shape, same D-8 intent (a stable namespace discriminator, not a security boundary). Existing project convention overrides the spec's illustrative hash choice.
Alternative
Excluding the driver from the security preset — weakens a repo-wide guarantee to preserve a cosmetic detail of the spec.

WorkosPennantDriver — PHPStan level 7 narrowing applied to the spec's authoritative class body

Context
The spec calls its §4.1 code "the authoritative implementation, not illustrative pseudocode", but three constructs fail this repo's PHPStan level 7 gate: $scope->workos_id ?? null on Authenticatable/Model interface types, arithmetic on the untyped cache payload ($cached['cachedAt']), and $flag->slug on the untyped generator autoPagingIterator() yields.
Decision
Behavior-preserving narrowing: data_get($scope, 'workos_id') + is_string (routes through Eloquent __get exactly like property access); a cachedEntry() helper returning array{slugs: list<string>, cachedAt: int}|null; instanceof Flag inside the pagination loop; 'user'|'organization' docblock union on WorkosFeatureScope::$type so fetchFromApi's match is exhaustive. Also hardened resolveFromClaims with an is_array($claims['feature_flags']) guard — a malformed claim now falls to the API path instead of fataling in in_array.
Alternative
Transcribing the spec body verbatim — fails composer analyse (the phase's own validation command), which the context map's build notes anticipated.
